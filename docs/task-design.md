**当前定案：Owner 管理多个独立 Task，每个 Task 由一个 Executor 完整交付，不做父子 Task 或任务树。** Executor 可以使用内部 subagent 完成拆分，但不通过 Task 模块继续向下派单。Owner 信任 Executor、主动读取进度，不做反向消息汇报；Executor 可以直接与用户澄清并修订任务。派单消息只携带 Task ID，前端通过约定的引用格式展示 Task 卡片。

以下保留讨论脉络。第 4、5 节记录曾讨论但当前不采用的角色演变和父子任务设想，不是当前设计要求；工作模式与范围以本段和第 15 节为准。

**范围更新：** 已有 Executor session 追加 Owner 能力较罕见且复杂，用户决定当前不做，后续由 [#2](https://github.com/waksana/cockpit-task/issues/2) 跟踪。本文保留这一产品设想，但它不再是当前 MCP、skills 或宿主能力的交付要求。

**派单方式更新（节点 2）：** 用户选择登记与指派分开，并进一步确认：新建 Executor 使用独立 Task MCP 工具，由它通过宿主创建 session 并配置执行能力，不由 Owner 自行拼装或检查底层能力。Owner 决定新建还是选择已有 session；指派 MCP 工具确认目标当前能力、更新 Task 的执行归属、发送 Task ID。Task 登记、session 创建、指派是独立操作，不提供登记后自动创建并派单的组合入口，普通记录编辑不发消息。下文早期的自动创建设想不再作为要求。具体装配方式在宿主接入节点核实，不假定能够无条件注入。

**最新范围收缩（节点 2）：** 用户因复杂度和实用率移除续办、改派；Task 首次指派后不替换 Executor，已结束 Task 不恢复执行。`task_read` 按 Owner / Executor 的关注点提供不同默认内容，其他详情和历史按需读取。Task 模块只包含 Owner / Executor 两份角色技能；Coding / Research 是模块外的工作技能，不由 Task 维护或发布。

**普通更新不使用 queue（节点 2，后续已细化）：** 日常只更新 Task，不排队发送要求、提醒或 cue。重要更新的显式强制对齐允许 Task ID 入队后主动推进，见下方最新决定；首次派单不擅自中断忙碌目标。

**宿主与访问模型更新（节点 3）：** 用户确认前端和 MCP 新建 session 都应选择角色，由系统注入对应 MCP。session 有相应工具即可操作其他 Task，不按 Owner / Executor 归属限制读写，不建立通用可信 caller 或逐 Task ACL。角色分工、作者与确认记录不等于访问控制。不新增原子排他控制接口；后续确认本体可将原生队列推进组合封装为通用 MCP。

**角色与复用（节点 3）：** 本体创建 session 时选择角色，MCP session 列表同时带出该角色。只复用已具备 Executor 能力的 session；指派时检查，不临时补装角色、Skill 或 MCP。角色记录持久保存并支持冷恢复，但列表标签不等于当前能力就绪。需要新的 Executor 时由独立创建工具完成创建和装配，不在指派失败后自动另建。

**创建时多角色（节点 3）：** 用户确认同一模块也允许多选，Task Owner 和 Executor 可以创建时一起选择。工具取并集、同一资源去重，指令保留来源及确定顺序；不静默覆盖冲突资源，不声称能自动识别所有自然语言矛盾。多角色不放宽单项未结束执行任务的限制，不引入任务树或运行中追加角色。

**模块 HTTP 与 MCP（节点 3）：** 模块自己实现 HTTP MCP，在本体挂载入口，并提供 MCP 配置供角色装配使用。Task 普通 HTTP API 给卡片或其他界面，HTTP MCP 给 agent，两者共用业务操作和数据。宿主不另建模块业务工具注册表，也不把它们并入本体 MCP；不新增独立 Task daemon 或 dashboard。

**角色作为能力入口（节点 3 调研）：** 模块通过角色向本体提供 Skill 与 MCP 配置，选择角色后由本体一并装配，无需用户再分别配置。SDK 1.0.13 已支持会话级技能目录、HTTP MCP 和工具子集及冷恢复参数；本轮宿主实现补充角色声明、创建装配和持久选择。Skill 可用不等于正文已提前加载，保持角色 System Prompt 与按需 Skill 配合，不为多角色建立另一套 custom agent 系统。

**角色指令合并：** 本体按确定顺序、标明模块与角色来源汇总原始指令，使用 SDK systemMessage 的 append 模式追加到主 agent 的 system prompt，不覆盖基础指令、不用模型摘要改写；Skill 正文仍按原生机制加载。

**队列推进历史决定（已被页首后续决定替代）：** 其他 session / subagent 消息保留。本体增加通用 MCP，逐轮中断并让原生接续，始终追到运行期间最新的队尾；后续队列耗尽时停止中断，保留最后轮次驱动 session 继续执行，不要求 idle。建议 Owner 先将 Task ID 入队一次再调用；新消息若在期间到达，也纳入推进，不保证最后一条仍是 Task ID。不是删除或复制重发消息，也不在操作完成后继续监视。此前“直到 idle 再发 Task ID”的方案被此决定替代，当时采用 `cockpit_advance_queue`。

**强制对齐的触发条件：** 上述循环是例外处理：只有 Owner 真正判断这次更新非常重要、不能等待正常同步点时才明确发起。普通更新只改 Task；未 ACK、revision 变化或工具提醒不会自动触发中断。是否重要由 Owner 判断，不由 Task 模块规则、helper 或后台循环判断。

**循环的等待边界：** 用户选择不设业务超时，持续推进到动态队尾耗尽或调用方取消。取消只停止继续中断，不清队列、不取消目标 session；原生结果未知仍须停止并报告，不能无限重试。用户已选择操作 ID 承载：同一个 MCP 支持启动、查询、取消，启动及时返回，单次连接断开不等于取消。

## 1. Task 从什么问题出发

用户的起点通常不是“我要创建一张任务卡”，而是对一件事情或一个领域产生了看法。

例如，用户看到一个 dashboard、一个 APP，想改进它。用户需要先找到负责这件事的入口，与它讨论和澄清，再由它安排具体执行。

典型过程是：

```text
看到一个领域或产品，产生想法
    → 找到负责它的 Owner
    → 与 Owner 澄清
    → Owner 建立工作记录并委派 Executor
    → 用户也可以直接与 Executor 讨论具体事宜
    → Executor 在内部组织工作，完整交付
```

Owner 通过 Task 或类似的工作记录，追踪自己负责范围内列出的事情。Task 要衔接的是想法、澄清、委派、执行和成果，而不只是保存待办清单。

## 2. 名称先服务于理解，不急于定稿

本轮暂用以下名称：

| 名称 | 当前讨论中的含义 |
| --- | --- |
| Owner | 某件事或某个工作范围的负责入口，负责澄清、安排、追踪和判断成果 |
| Executor | 承接一项具体工作的 session，对该项工作的完整执行负责 |
| Task | 记录工作约定、责任、变化、动态和结果的共同记录 |

用户还提到 Domain Owner、Job Owner、Orchestrator、领域专家、Work Item 和 Workstream。它们并不都指同一类概念，暂不统一成正式命名，也不据此创建新的产品实体。

节点 1 已确认正式统一使用 Owner / Executor，对应字段 `owner` / `executor`，不保留 Coordinator / Assignee 两套接口名称。旧实现的 Commander / Owner 仍是历史术语，不能将其中的 Owner 机械映射为新版 Owner。

## 3. 用户可以直接参与执行过程

Owner 是负责入口，但不是用户与 Executor 之间必须经过的中转站。

Owner 澄清并委派后，用户可以直接与 Executor 讨论实现细节、补充信息、澄清要求。Executor 不是只能接收固定命令、上报进度的终端。

双方讨论形成的新要求，应回到共同的 Task 中，不能只留在某一个 session 的聊天里，使实际执行约定与任务记录分离。

## 4. 历史设想：责任角色叠加（当前不做）

本节保留讨论过程。用户最终选择由 Executor 完整交付，不通过追加 Owner 能力继续派发子 Task；角色追加仅留在 #2。

Owner 和 Executor 不是 session 终身固定、互相排斥的类别。

一个 session 最初承接上游委派，是该 Task 的 Executor。随着用户与它深入讨论，它可能继续委派其他 Executor 做调研或具体工作，因而又承担下游工作的 Owner 职责。

这不是 Executor 转换成 Owner，也不是放弃原来的工作，而是责任叠加：

```text
相对上游工作：这个 session 是 Executor
相对它委派的下游工作：同一个 session 是 Owner
```

此前使用的“升格”应按这种叠加理解，不表示必须更换 session、撤销原身份或建立固定职级。

一个 Task 仍应有一个对其整体负责的执行 session。进一步委派不应让原工作的整体责任消失；具体如何验收和汇总下游成果，仍需继续明确。

## 5. 工作可以拆分，但当前不形成父子 Task

大工作未必能在一开始就拆清楚。随着讨论深入，才逐渐显露出可分别处理的问题。

例如，“设计 Task”可以展开为：

| 问题范围 | 可能继续展开的内容 |
| --- | --- |
| Task 本身是什么样的 | 协作模型、工作流程、skills、agent 操作工具等 |
| Task 如何接入 | 如何让上述能力在目标环境中可用 |

讨论中曾考虑将这些部分委派为父子 Task。用户最终确认：当前不做父子 Task，原 Executor 完整负责，可以在内部拆分步骤或使用 subagent。

因此，问题分类、实施步骤、每份 skill 或每个工具都不必成为单独 Task。Owner 可以管理多个独立 Task，但不为一个 Task 的内部执行建立任务树。

当前不设计父子状态汇总、递归派单或任务级联。内部 subagent 是 Executor 的执行细节，不登记为 Task，也不转移其整体交付责任。独立 Task 如需关联，可使用普通引用，不产生父子关系或自动调度。

## 6. 创建时的角色，也是工作能力的组合

用户设想，模块注册可选择的角色，声明对应的 skills、MCP 和系统 prompt；新建 session 时选择角色，使其获得相应的工作指导和工具。角色多选及组合后的行为需要单独设计，不能默认只是拼接所有内容。

以领域负责入口为例，Owner 类角色的 skill 指导它如何澄清需求、建立 Task、创建执行 session 和委派工作。按节点 2 的最新确认，独立的 Task MCP 创建入口负责 Executor session 的创建和能力配置；另一个指派入口负责关联已有 Task 并发送 Task ID，不能合并成隐式启动。

用户不需要每次手动为 Executor 重新拼装任务背景、skills 和工具。

这里的“自动派发”是明确派单操作内部的准备过程，不是系统自行寻找任务或决定开工，也不意味着每次保存、修订 Task 都会唤醒 session。

## 7. 工具能力要与职责匹配；后续追加暂缓

本节的角色追加设想已移至 [#2](https://github.com/waksana/cockpit-task/issues/2)，当前不实现。

用户明确提出，角色区分不只是说明文字，还涉及实际可用的工具：

| 角色能力 | 期望用途 |
| --- | --- |
| Owner 能力 | 创建 Task、委派和组织工作 |
| Executor 能力 | 更新自己承接的 Task，包括动态、结果，以及与用户澄清后的内容 |

因此，一个 Executor 后来需要承担 Owner 职责时，仅改变名称或告诉它“你也是 Owner”还不够。它需要追加相应的工作指导和工具，同时保留原来的执行责任与能力。

用户提出的候选入口是：由 Task MCP 提供一个操作，让当前 session 为自己追加 Owner 能力，再开展明确的下游委派。

这个提议不是接管其他已有 Task，也不应把“启用能力”与“实际派单”混成一个隐式动作。

仍需决定这是否是所有 Executor 都能自助启用的能力，还是需要用户或上游 Owner 批准。如果允许自由启用，角色工具区分主要体现按需装配，不能同时把它描述成阻止 Executor 获得 Owner 能力的权限隔离。

角色说明、skill 和工具是否可见，也不能替代任务归属和操作范围的保护。

## 8. Owner 与 Executor 共同维护当前工作约定

Task 不只是 Owner 单向下达的命令，也不是 Executor 只能填进度的表格。

Owner 可以修订任务；Executor 也可以直接找用户澄清，将新的信息和要求写回自己承接的 Task，形成新版本，不必再经 Owner 转述。

两方维护同一份完整、当前有效的工作约定，修订历史保留修改人、时间和原因。旧版本的确认或成果，不能覆盖新的要求或结束事实。

2026-09-20 用户进一步明确：完整任务说明命名为 `description`，始终保存最新正文；`revision` 仅是 description 的版本，每次修订对应一条 `changelog`。执行动态属于独立的 `activity`，每条指向所依据的 description 版本；Executor 的 `acknowledged_revision` 也只确认 description 版本。状态、进度和首次指派本身不推进 description 版本，不进入它的 changelog。此前将归属变化也推进 revision、用通用 history 混合所有操作的草案作废。

用户再次确认：**description 和 changelog 属于 Task 定义，activity 属于 Executor 执行时添加的活动。** 不把定义修订、Owner 操作和 Executor 活动混成一个流水账；Owner 改要求不自动生成或冒充 Executor 的执行活动。

节点 2 已确认：当前 Executor 可以补写旧版 description 对应的 activity，但旧版状态和成果不能保存；拒绝原因明确为 description 有新更新，需要先读取并 ack。**任何 Executor 对 Task MCP 的调用都应检查定义更新，并提示尚未确认的新版本**，不只在特定工具或成功报告时检查。提醒不自动确认，不发送反向消息，也不把原操作的失败或部分应用隐藏掉。

节点 2 已确认：**ACK 与改变状态是两件事，不混合。** 首次及后续 ACK 均只更新 Executor 确认的 description 版本，不自动进入 in_progress、解除 blocked 或生成 activity；实际开始执行或改变状态必须明确操作。Executor 自己修订后的自动 ACK 同样不附带状态变更。

两种修订在知晓方式上有所区别：

- Owner 修改后，Executor 之后读取并确认最新要求。
- Executor 根据用户澄清亲自修改时，在修订成功的同时直接确认自己写成的新版本。

以上确认规则已由用户在节点 1 明确。该确认不能延伸到之后其他人产生的新版本，也不能跨过身份或并发冲突。

**重要修订后的主动对齐：** Owner 修改了重要要求后，应查看 Executor 的运行情况及最近在做什么，再判断是否需要打断，让 Executor 重新读取并对齐 Task。这是 Owner 根据实际情况作出的明确决定，不是修订操作自动打断或发消息。可读取的动态必须如实区分原生活动与 Task 报告，不能扫描聊天或把未知当作已知。

若 Owner 判断更新非常重要、必须立即重新对齐，可先明确入队一次 Task ID，再调用本体队列推进 MCP；它动态追最新队尾并保留最后轮次，不要求 idle。普通更新仍只修改 Task，不把完整要求复制进队列，不自动触发强制对齐。

Executor 的正常职责是修订所承接工作、报告状态和成果，并按约定取消；但用户在节点 3 明确不以归属作为权限限制，具有工具可以操作其他 Task。仍不能替换已绑定 Executor、恢复已结束任务或把工具可用当成实际执行者已经确认要求。具体数据规则见 Schema 草案。

## 9. 保留的简洁协作原则

本轮没有推翻以下已讨论方向：

**共同记录，而非消息转发。** 要求直接修订 Task，动态和结果直接写回。Executor 不向 Owner 发送进度、阻塞或完成消息，Owner 按需读取；需要用户决策时直接向用户澄清。修订不自动打断执行，是否需要中断由负责方判断。

**少量固定信息，其余按需表达。** 保留身份、标题、完整 description、责任双方、状态、结果、动态、description 版本与 changelog、Executor 确认版本等核心概念，不强制每种工作填写庞大表单。

**动态与运行状态分开。** 最新一条 activity 就是最新情况，不重复维护另一份进度摘要。Task 状态与 session 是否运行是两回事；报告动态与原生活动必须区分，未知不伪装成实时。这是记录语义，不要求 Task 自带看板前端。

**沿用简洁状态词汇。** 当前仍以 `todo / in_progress / blocked / in_review / done / cancelled` 表达工作状态，不做父子状态联动。

**Executor 可直接完成。** 用户在节点 1 确认：Executor 完成当前约定后，可以写入 outcome 并直接将 Task 标为 `done`，无需等待 Owner 验收。`in_review` 仅用于任务本身需要的评审步骤，不是所有 Task 的强制关卡；进入该状态也不自动通知 Owner。

**可先登记再派单。** 用户在节点 1 确认：Owner 可以先登记一个未分配的 `todo`，暂不创建 Executor，之后再明确派单。登记与启动执行是不同动作，派单沿用同一 Task ID。

**不做续办和改派。** 节点 1 曾讨论并确认这两项能力；用户在节点 2 明确因复杂度和实用率去掉，当前不设计对应工具、参数或后端机制。已有历史保留，已结束 Task 不恢复执行，已绑定 Executor 不替换。

**取消可由双方记录。** 用户在节点 1 确认：Owner 可以取消；当前 Executor 收到用户取消要求时，也可以取消本任务。取消后不接受继续报告为进行中或完成；记录取消不等于已经停止 session，必要的中断另行处理。

**一个 Executor 同时只承接一项未结束工作。** 用户在节点 1 确认：同一个 Executor session 一次最多承接一个未结束 Task，完成或取消后可承接其他 Task，不终身绑定；记录已结束也不代表原生 session 已空闲。

**执行前主动同步。** Executor 在开始、重要阶段之间、重要操作前、交付前及恢复工作时检查当前约定，而不是高频轮询，也不只依赖首次派单文本。

**角色技能与工作技能正交且分开提供。** Task 仅维护 Owner / Executor 两份角色技能，说明如何协作；Coding、Research 等外部工作技能说明如何完成具体工作，不包含在本模块。一个任务可以组合不同工作方法，Task 核心不理解 GitHub、固定工程流程或业务类型，也不固定工作技能名单。

**Task 是协作工具，不是自动监工。** agent 根据用户意图主动澄清、委派、更新和判断；记录、关系或状态变化本身不构成新的执行授权。

## 11. 设计工作划分：Task 与宿主分别负责什么

此前讨论曾暂不包含 Task 前端；用户后续明确需要展示 Task 的前端卡片，因此增加卡片设计工作。卡片不等于完整独立看板或管理页面，展示位置与交互尚未确定。用户以 dashboard / APP 为例描述需求来源，也不意味着 Task 必须实现这样的完整页面。

可以将接下来的设计工作划分为以下几个任务。这里是设计范围整理，不是已经创建或派发的执行任务。

| 设计任务 | 需要回答的问题 | 归属 |
| --- | --- | --- |
| Task Schema | 核心字段、Owner / Executor 责任关系、状态、修订与确认、动态与成果如何表达；哪些固定，哪些开放；不含父子关系 | Task |
| Task 后端模块 | 如何维护共同记录、责任关系、修订历史和操作一致性；如何承载 MCP 所需的业务行为，与宿主职责分界 | Task |
| Task MCP | agent 使用哪些工具；如何创建 Task 并派发 Executor session；每项操作的输入、效果和结果如何表达；不含自助追加 Owner | Task，涉及 session 与角色时使用宿主通用能力 |
| Skills | 如何根据 Task Schema、协作流程和 MCP 工具契约指导 Owner / Executor 行为 | Task 仅维护角色技能；工作技能由外部提供 |
| Task 展示卡片 | 如何呈现任务、责任关系、最新动态及结果，如何读取同一份 Task 记录；位置和交互待设计 | Task 前端 |
| 角色注册与声明 | 模块如何提供角色；每个角色声明哪些 skills、MCP 和系统 prompt；角色与具体 Task 的责任关系如何区分 | 宿主通用能力，Task 是使用者 |
| 创建 session 时选择角色 | 用户创建和 agent 派单如何选择角色；无角色选择时的行为；多选角色如何组合和呈现结果 | 宿主通用能力 |
| 已有 session 追加 Owner（暂缓） | 保留设想，当前不设计为必须交付的能力；后续见 #2 | 后续增强 |

Task MCP 是独立的设计任务，不只是把后端接口逐一包装成工具。它需要面向 agent 的使用过程组织操作；后端维护这些操作背后的业务记录和一致性，宿主负责真实 session 与角色能力的装配。Task 卡片属于 Task 前端；创建 session 时的角色选择界面仍属于宿主。

角色组合至少需要明确以下问题，而不是先假定已有答案：

- 同一模块的多个角色、不同模块的角色是否都可以同时选择。
- skills 和 MCP 重复或同名时如何处理，工具集合如何组合。
- 多份系统 prompt 如何组合，顺序和矛盾如何处理，以及如何保留已有工作指令。
- 创建时哪些组合需要明确拒绝；与后续追加的衔接留待 #2，不为未来能力预建机制。
- 选择了角色、能力实际可用、承担了某项工作的责任，分别意味着什么。

这些问题应先回顾已经存在的角色设计，再判断哪些原则可沿用、哪些需要调整，不从零另造一套，也不把旧方案直接当作当前定稿。

## 12. Task MCP：设计可使用的工作操作

用户进一步提出，需要专门设计 Task MCP，例如创建 Task 时自动创建一个 Executor session。曾讨论的“通过 MCP 为自己追加 Owner 能力”已暂缓至 #2，不纳入当前工具集。当前操作如何完成，是待开展的设计工作，不在本文预定工具名、参数或具体实现。

| 操作场景 | 需要明确的设计内容 |
| --- | --- |
| 创建 Task 并派单 | Owner 填写工作约定后，由明确的操作创建 Task、创建执行 session、选择 Executor 角色并关联工作；登记但暂不开工是否另有入口 |
| 读取与承接 | 如何读到自己相关的任务、完整当前要求与变化，如何明确承接并确认版本 |
| 修订与更新 | Owner 或 Executor 如何修订共同约定，Executor 如何记录动态、阻塞和结果；区分内容修订与一般工作报告 |

这些场景来自已经讨论的协作流程，用于检查 MCP 设计是否覆盖完整使用过程，不代表必须各自对应一个工具。Executor 自助追加 Owner 的场景留在 #2，不为它提供当前工具或隐式替代流程。

MCP 设计需要同时说明正常路径和未完成时的含义：

- 创建 Task、创建 session、角色可用、派单受理、Executor 承接是不同事实，不能以其中一步成功冒充全部完成。
- 若操作只完成一部分或结果未知，应能看清已经发生的事情，不能因重试而重复创建 Task 或 session。
- 工具由角色装配；Task 目标、操作者记录和定义版本分别表达，不把分工字段当作访问权限。任何调用仍须遵守版本和状态规则。

这一设计工作应先明确 agent 想完成的动作、动作的边界和成功条件，再确定 MCP 工具如何组织，不预设固定工具数量，也不恢复旧版整套工具和通知流程。

## 13. Skills 与 Schema、工作方式、MCP 配套设计

用户进一步明确：skills 也需要作为设计任务，与 Task Schema、Task 的工作方式、MCP 及其工具 schema 配合，不能等其他部分完成后再补一份泛泛的角色说明。

这里需要区分两类 schema：

| 契约 | 表达什么 | Skills 如何配合 |
| --- | --- | --- |
| Task Schema | 工作约定、责任关系、状态、修订、确认、动态与成果等共同记录 | 教会 agent 如何理解记录、维护哪些信息，以及如何判断当前责任和版本 |
| MCP 工具 Schema | 每项操作接受什么输入、返回什么结果，以及失败或未完成如何表达 | 教会 agent 何时调用、如何准备信息、如何理解结果，以及何时必须先读取或澄清 |
| Task 卡片格式 | agent 如何在回复中正确引用或输出一个可展示的 Task 卡片 | 明确使用时机、必要信息、正确示例和错误示例，与前端识别规则一致；具体格式待设计 |

Task 的工作方式把两者连起来：先澄清、再记录或派单，执行中同步与更新，最后交付成果。Skills 应指导这些行为，而不是仅罗列字段或复制工具参数文档；当前不指导 Executor 调用尚未提供的 Owner 追加能力。

角色技能与工作技能仍保持正交：

- Owner 类技能指导澄清、创建与委派、修订、追踪、整合和判断成果。
- Executor 类技能指导承接、主动同步、直接向用户澄清、修订本任务、报告与交付。
- Coding、Research 等外部工作技能指导具体工作方法，与角色技能组合，但不包含在 Task 模块内，不把各自的业务要求变成所有 Task 的必填字段。

配套设计至少应保证：

- Skill 描述的操作确实有相应工具支持，不要求 agent 调用当前角色没有的能力。
- Skill、Task 状态与工具结果使用一致的术语，不把“已创建 session”“已派单”和“已承接”混为一谈。
- 角色叠加后，Owner 与 Executor 的指导可以共存，不因新增角色而遗忘上游责任。
- 修订与确认、用户澄清、部分完成和未知结果等关键场景都有一致的行为指引。
- Agent 需要展示 Task 时，skill 应指导它产生正确的卡片格式，而不是自由编造看起来像卡片的文本。格式规范须与前端共同设计，不在 skill 中另定一套。
- Skill 负责行为指导；工具仍保护版本、状态、ACK 与幂等，但不追加逐 Task 归属鉴权。

这些部分应围绕同一组协作场景共同迭代。既不让 skill 凭空承诺工具能力，也不让工具字段反过来迫使所有工作采用不必要的流程；具体内容和接口留待各项设计展开。

## 14. 范围收束：Task 设计与宿主通用能力

用户将本轮范围收束为两个相互配合的层面。角色注册，以及 skills、MCP 和系统 prompt 的注入，属于宿主提供的通用能力，不应由 Task 私自实现另一套会话配置机制。

| 层面 | 设计内容 |
| --- | --- |
| Task Schema 与工作方式 | 独立任务的共同记录、责任关系、状态、修订与确认，以及从澄清到完整交付的协作流程；不做任务树 |
| Task 后端模块 | 承载工作记录及其业务操作，维护归属、历史和一致性 |
| Task MCP | 面向 agent 组织读取、更新、修订、创建与派单等操作，设计工具 schema 和结果语义；追加 Owner 暂缓 |
| Skills | 仅提供 Owner / Executor 角色指导，配合 Task Schema 和 MCP；外部工作技能不纳入本模块 |
| Task 展示卡片 | 基于共同记录呈现 Task；不另行维护一套前端进度或要求 |
| 宿主通用能力 | 模块角色的注册与声明；创建 session 时的角色选择及多选组合；对应 skills、MCP 和系统 prompt 的装配与生效；已有 Executor 追加 Owner 暂缓 |

Task 声明自己的角色内容，并通过宿主能力完成 Executor 创建与角色配置。宿主不理解 Task 的业务关系、工作状态或成果判定，也不把 Owner / Executor 写成所有模块必须采用的角色。

上述清单是目前讨论得到的主要设计范围，不是已经完成的接口规格或执行派单。Task 包含展示卡片这一前端工作，但不据此扩大为完整独立管理页面；宿主角色选择入口与 Task 业务工具分别归属各自层面。接下来各项设计应在这一边界内互相配合，而不扩展为全面模块重构。

## 15. 最新决定：自上而下、充分信任、Task 是唯一工作记录

用户在设计 review 后进一步明确以下工作模式。这些决定收束前文的开放讨论，优先于早期相反的范围描述。

### 独立 Task，Executor 完整负责

用户最终确认：Owner 管理多个独立 Task，每个 Task 交给一个 Executor 完整完成，不做父子 Task 树。原先“自上而下”的协作方向保留，但不再将它建模为递归任务层级。

Executor 可以内部拆分、使用 subagent、与用户讨论，并完整交付原任务；不需要升格或继续派发子 Task。已有 Executor 追加 Owner 能力只作为后续 issue #2 保留。

上游对下游充分信任，不以逐级审批或反复要求下游证明工作作为默认协作机制。归属保留为分工，版本与并发一致性仍由工具维护；用户进一步明确不做逐 Task 访问控制，角色能力需要正确装配。

此前 review 提出的审批、验收或反向协调建议，不能未经确认就变成强制流程。成果整合和状态含义仍可设计，但不能据此建立默认的不信任或审批关卡。

### 上游主动读取，没有反向消息汇报

上游主动了解下游进度，通过读取对应 Task 获得最新情况。下游把进展、阻塞、澄清和结果写入 Task，不向上游发送消息或提出额外汇报请求。

消息只承担明确派单的作用；记录变化、阻塞或完成不产生反向通知，也不需要自动唤醒上游。这里的“主动问进度”通过读取共同记录完成，不另建一条问答消息链。

强制对齐使用同一 Task ID 引用，可明确入队后主动推进，但不追加第二套工作要求。普通更新由 Executor 在同步点读取；只有 Owner 判断非常重要时才执行这项例外，不增加日常排队指令通道。

上游何时读取属于其工作行为，不因此引入后台监工、自动轮询或调度器。

读取不能一股脑返回所有字段和历史。Owner 例行关注执行者、状态、最新报告活动、确认差异与成果是否就绪；Executor 开工和同步时需要完整当前要求、资料、版本/ACK 与工作归属。两份 skill 默认选择不同 view，工具不按身份或归属限制可读内容。具体视图草案见 MCP 契约。

### 所有工作信息归 Task，派单消息只有 ID

任务背景、完整要求、约束、澄清结论、修订、动态、阻塞和结果都应记录在 Task 上。资料或成果可以通过 Task 中的引用关联，不能只留在某次派单文本或某个 session 的聊天里。

派单消息只携带 Task ID，不附带目标摘要、额外要求、其他上下文或重复的任务说明。按后续提出的卡片约定，ID 可以使用统一的 Task 引用格式包裹；“只给 ID”限制的是业务内容，不要求消息必须是裸 ID。Executor 通过已有角色能力读取这个 ID 对应的当前 Task，再承接工作。

这意味着，派单前必须让 Task 本身足够完整，并准备好执行者读取任务的能力；不能依靠首条消息临时补全。用户仍可直接与 Executor 澄清，但影响工作的结论必须写回 Task。

Task 是工作约定和进展的唯一记录来源，聊天不是第二份任务数据库。角色 skills 和通用工作指导仍由角色能力提供，不混进每次派单消息。

### 增加 Task 前端卡片

用户明确需要一个可以展示 Task 的前端卡片，这是单独的前端设计工作，更新此前不做 Task 前端的范围。

卡片应呈现 Task 的真实记录，不生成或维护另一套进度摘要。它放在哪里、展示哪些字段、是否展开详情，尚未确定；不包含任务树，也不扩展为完整看板、编辑器或调度界面。

### Skills 也要指导正确的卡片输出

用户进一步明确，skill 应包含如何让 agent 产生正确 Task 卡片格式的指导。卡片不只是前端展示设计，还需要一份 agent 能遵循、前端能识别的表达约定。

该约定需要明确何时展示卡片、如何关联真实 Task、所需格式与示例，以及引用不可用时如何如实表达。具体语法尚未决定，表达与渲染的方向见下一节。

卡片表达不能成为另一份工作记录，也不能由 agent 填写的展示内容覆盖 Task 的真实数据。面向用户回复时的引用与向 Executor 发送的派单可以使用同一格式；派单仍只携带 Task ID，不因卡片展示而附加业务内容。

### Task 引用格式与后端驱动的卡片

用户提出：约定一种包含 Task ID 的格式来发送 Task；前端识别这个格式并渲染卡片，卡片可以通过 ID 从后端获取 Task 数据。

```text
消息中的约定格式：Task 引用 + ID
    → 前端识别该引用
    → 通过 ID 向 Task 后端读取记录
    → 渲染 Task 卡片
```

这样，消息传递的是引用，而不是复制标题、状态、description 或成果。Agent 根据 skill 产生正确的引用格式；Executor 读取对应 Task 开工；前端读取同一份记录用于展示。呈现卡片不改变任务，也不自动触发执行。

该方案下，卡片展示的是读取时的 Task 数据，不应被理解为消息发送时的历史快照。刷新时机、历史版本入口、加载失败或不可访问时的表现仍需设计，不能因一次读取就宣称持续实时更新。

此前“卡片只用于面向用户回复”的区分据此更新：派单引用也可以被前端识别成卡片；区别在于消息用途，而不是必须使用两套格式。具体标记语法以及前端如何提供这一展示能力，留待专门设计。

## 核心观点

Task 围绕有负责人的事情组织协作：Owner 澄清并派单，一个 Executor 完整交付；用户可以直接与 Executor 深入讨论，工作约定随之修订。Owner 信任执行者并主动读取共同记录，不需要反向消息、角色升格或任务树。Task 让约定、责任、变化和成果可追踪，而不替人和 agent 决定下一步。
